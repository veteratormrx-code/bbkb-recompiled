# Нагрузочная проверка

Два канала проверки: инструментованный `#stress` в `:ime-harness` (настоящие `MotionEvent` по
координатам клавиатуры, смешанный английский/русский набор, скрытие и показ клавиатуры) и внешний
сэмплер памяти `tools/qa/Invoke-StressTest.ps1`, который каждые 20 с снимает PSS, native heap и
host-счётчики процесса эмулятора.

## Итоговый прогон: форк, 10 000 клавиш

```
keys=10003 elapsed=1708s rate=5.9/s lost=0 duplicated=0
panels=0/33 keyboardCycles=25 languageSwitches=12 ruAvailable=True
latency p50=0ms p95=13ms p99=20ms (samples=1458)
memory: guest PSS 266 -> 296 MB, native heap 32 -> 34 MB, host 3456 -> 3755 MB, threads 226 -> 244
```

| Метрика | Значение |
|---|---|
| Нажатий | 10 003 за 28 мин 28 с |
| Потеряно символов | 0 |
| Дублировано символов | 0 |
| Падений и ANR | 0 (`logcat -b crash` пуст, `am_anr`/`am_crash` за прогон нет) |
| Циклов скрытия/показа клавиатуры | 25 |
| Переключений языка | 12 |
| PSS клавиатуры | 265–387 МБ, финал 296 МБ (+30 МБ к старту) |
| Native heap | 32 → 34 МБ |
| Рабочий набор хоста | 3456 → 3755 МБ, максимум 3755 МБ |
| Потоков хоста | 226–277, финал 244 |

В этом прогоне PSS не рос монотонно. После пика 387 МБ при смене фазы языка значение возвращалось к
265–294 МБ. Рабочий набор процесса эмулятора вырос на 299 МБ (8,7 %). По одному ряду нельзя выделить
причину роста или оценить утечку в IME. Полные сэмплы —
`docs/testing/artifacts/audit-2026-11-24/stress/fork-memory.csv` (89 точек), отчёт прогона —
`stress/fork-stress.json`, журнал инструментирования — `stress/fork-instrument.txt`.

## Память хоста: что было исправлено

До правки процесс эмулятора доходил до 13 046 МБ рабочего набора, 17 160 МБ private bytes и
1 635 потоков после ~2 ч автоматизации, и хост уходил в своп при свободных 3,9 ГБ из 32 ГБ. В этом
прогоне тот же сценарий держит 3,5–3,8 ГБ рабочего набора и 226–277 потоков. Механизм описан в
[ограничениях](known-limitations.md): обрезка рабочего набора (`-Action Trim`), фоновый сторож
(`-Action Watch`, порог обрезки 4,5 ГБ, порог перезапуска 7 ГБ) и запуск без камер и метрик.

## Чего прогон не показал

- **Совпадение текста.** Для каждой порции тест сравнивал длину ожидаемого и фактического текста. Подмена символа, перестановка или взаимная компенсация пропуска и дубля могут пройти эту проверку.
- **Панели не пройдены: `panels=0/33`.** Харнесс ищет элементы панелей по
  `contentDescription` (`Emojis`, `Clipboard`, «Select, cut, or copy», `Keyboard mode`) — так они
  опубликованы у 4PDA-мода. У форка панель инструментов рисуется одним `View`
  (`unified_input_menu_bar_view`, `clickable=false`) и по элементам в accessibility-дерево не
  раскладывается, поэтому поиск не находил цель и цикл считался неуспешным. Это ограничение
  канала проверки, а не отсутствие панелей: панели форка открываются касанием и проверены
  отдельно координатными прогонами. После прогона в новой компактной панели появились `ImageButton`
  с текстовыми описаниями. Нужен повтор с открытием этой панели, доступными селекторами и запасным
  координатным маршрутом для рисуемой поверхности.
- **Задержка p50 = 0 мс.** В цикле ожидания `while (editorText().length < expected.length)` текст
  успевает появиться до первого замера, поэтому медиана упирается в ноль, а p95/p99 отражают
  только «медленный хвост». Абсолютные задержки корректнее брать из сравнительного прогона
  автозамены ([autocorrect-benchmark.md](autocorrect-benchmark.md)), где замер идёт от нажатия до
  коммита символа.
- Прогон выполнен только на форке. Upstream и мод в этом сценарии не гонялись: сравнение
  устойчивости к длительному набору не является свойством, которое различает сборки, а русская
  фаза на них недоступна (см. [автозамену](autocorrect-benchmark.md)).

## Предыдущие короткие прогоны

Два нажатия на Android 15 прошли. Прогон из 100 нажатий в одном случае недосчитался символа во
втором пакете. После замены APK другой прогон получил пустое поле. На Android 17 прогон из 100
нажатий прошёл за 15,098 с, а прогон из 10 000 нажатий был остановлен внешним `am force-stop`.
